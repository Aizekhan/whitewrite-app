## 0. Що змінилося від версії 2.0

Версія 2.0 описувала платформу як окремий продукт, який ще треба побудувати. Версія 3.0 фіксує важливий факт: більшість фундаменту вже існує всередині WhiteWrite. Там є Світ (канон) як єдине джерело правди, Біблія гри з картками, файлами й 3D-переглядом, AI-аналіз і продакшн-план. Тепер є і MCP-сервер, через який Claude Code бере завдання та здає результат.

Тому v3 — це не новий окремий сервіс, а архітектура «AI Game Dev Platform як модуль WhiteWrite». Нижче кожен розділ концепції v2 зіставлено з реальними компонентами: що вже працює, що працює частково і що лишається на наступні фази.

| Тема | Концепція v2 | Реальність v3 (WhiteWrite) |
|---|---|---|
| Джерело правди | Game Project Database | Світ worlds/{w} + канон entities/ + гра games/{g} у Firestore |
| GDD | Інтерактивний GDD із розділами | 14 стандартних розділів Біблії + власні; AI-аналіз (готовність, суперечності, питання) |
| Assets | Asset Manager + Asset Plan | Розділи Ассети/Матеріали/Анімації/Звук, реальні файли в Storage, 3D-перегляд FBX/GLB/OBJ/STL |
| Roadmap | Phase → EPIC → Task | Етапи з воротами → завдання з критеріями, тестами, повʼязаними картками |
| Task Engine | Статуси, залежності, наступне завдання | games/{g}/tasks: todo → in_progress → review → done \| rework \| blocked |
| MCP | Перелік інструментів (чернетка) | 10 інструментів у проді, Streamable HTTP, ключ на гру |
| Review | Сервер перевіряє критерії | Сервер рахує check (критерії + тести), автор приймає або повертає |
| Change Request | Процедура погодження | submit_change_request → блок «Запити на зміни» у плані |
| Canon / Lore | Не було | Перевага WhiteWrite: один канон → багато ігор і книг |

## 1. Головна ідея (без змін) і наша перевага

Платформа знає, що треба створити, як це має працювати і яке завдання наступне. Людина — автор і ухвалює рішення. AI організовує, проєктує, виконує доступну роботу і контролює відповідність результату задуму.

Чого не було у v2 і що дає WhiteWrite:

- Канон світу як фундамент. Персонажі, локації, фракції, закони світу живуть у Світі, а не в GDD. Гра дивиться на канон «через себе»: гейм-поля сутності (HP, атаки, префаб) лежать у картці гри з canonRef, а не на сутності. Тому один світ може мати кілька ігор і книг без дублювання.
- Рушій реконструкції. Механізм впливу змін (Canon Change → Impact → Plan) вже існує для наративу. Його природне розширення — граф залежностей гри (§8 v2), коли зміна рішення показує, що треба переглянути.
- Inferred ≠ fact. AI-припущення йдуть у чергу на підтвердження і не стають «рішенням» самі. Те саме правило діє для імпорту нотаток і плану: автор відмічає, що прийняти.
- Біллінг і доступ. Токени, плани і feature gates уже є. Розробка гри доступна на планах з allowGameDev (worldbuilder, worldforge).

## 2. Архітектура: сервер — мозок, Claude Code — виконавець

Фундаментальне рішення v2 збережено. WhiteWrite не пише власного агента для Unity. Він тримає стан гри, план і контекст, а Claude Code працює в репозиторії Unity-проєкту своїми інструментами (файли, shell, git, Unity CLI) і звертається до WhiteWrite по MCP.

```
АВТОР (браузер)
  └─ whitewrite.com → Світ → Біблія гри (розділи, картки, файли, 3D, план)
        │  Firestore + Storage (worlds/{w}/games/{g}/…)
        │  Cloud Functions: gamedevPlan (import · analyze · plan)
        ▼
WHITEWRITE BACKEND  ── єдине джерело правди про гру
        │  functions:mcp  (MCP Streamable HTTP, Bearer wwk_…)
        ▼
CLAUDE CODE  (на машині розробника, у папці Unity-проєкту)
        │  читає/пише код і ассети, запускає тести, комітить
        ▼
UNITY PROJECT + власний Unity Framework
        │
        └─ звіт (submit_task_result) → review у Біблії → Прийняти / Повернути → наступне завдання
```

## 3. Модель даних

Усе зберігається у Firestore під світом. Ідентифікатори стабільні й непрозорі, а назви змінюються без розриву звʼязків.

| Шлях | Зміст |
|---|---|
| worlds/{w} | Світ: назва, тон, закони, факти. Власник — автор. |
| worlds/{w}/entities/{id} | Канон: kind (character/location/event/faction/artifact), name, slug, desc, стан… |
| worlds/{w}/games/{g} | Гра: назва, профіль рушія (engine.profile), власні розділи. |
| …/games/{g}/cards/{id} | Картка: section, title, status (idea/work/agreed/ingame), fields (+group — підзаголовок), note для Claude, files[], canonRef, planTask. |
| …/games/{g}/plan/current | analysis (GDD, готовність, суперечності, питання, рішення), plan (етапи → завдання), scaffold. |
| …/games/{g}/tasks/{taskId} | Завдання: milestone, title, detail, deps, owner, size, cards, accept[], tests[], prompt, status, progress, blocker, report, history[]. |
| …/games/{g}/executions/{id} | Журнал кожного виклику MCP (інструмент, завдання, час). |
| …/games/{g}/changeRequests/{id} | Запит на зміну рішення: what, why, proposal, impact, taskId, status (open/accepted/rejected). |
| mcpKeys/{sha256} | Ключ виконавця: uid, worldId, gameId, label, prefix, createdAt, lastUsedAt. Сам ключ не зберігається. |

> Відмінність від v2: сутності GDDSection, Asset, DesignDecision, VisualReference не окремі таблиці, а картки у розділах Біблії. Це простіше для автора: один тип обʼєкта, однаковий редактор, файли й статуси скрізь. Окремі поля (вимоги до ассета, рішення, обґрунтування) — це поля картки за схемою розділу.

## 4. Процес створення гри у WhiteWrite

| Фаза v2 | Як це зроблено | Результат |
|---|---|---|
| 1. Game Concept | Genesis світу (насіння, закони) + розділ «Огляд гри»; імпорт .md-нотаток | Світ + картки Огляду |
| 2. Visual Direction | Розділи «Референси», «Матеріали й текстури» з картинками; профіль рушія | Картки з файлами |
| 3. GDD | 14 стандартних розділів; «Оновити аналіз» → GDD, готовність у %, суперечності, питання | plan/current.analysis |
| 4. Technical Design | Розділ «Технічне» + профіль рушія; далі — Framework Registry | Картки Технічного |
| 5. Asset Production | Ассети й префаби (FBX/GLB, текстури), 3D-перегляд, підзаголовки; scaffold створює порожні картки «в роботі» | Каталог ассетів |
| 6. Roadmap | «Перегенерувати план» → етапи з воротами → завдання з критеріями, тестами, картками і промптом | plan + tasks/ |
| 7. Розробка | Claude Code по MCP бере завдання, здає звіт; автор приймає/повертає | Статуси, прогрес, картки «в грі» |

Стандартні розділи Біблії гри: Огляд гри, Лор гри, Механіки, Прогресія й економіка, Рівні й контент, Вороги й боси, Предмети й спорядження, Ассети й префаби, Матеріали й текстури, Анімації й VFX, Звук і музика, UI / UX, Референси, Технічне — плюс власні розділи і Продакшн-план. Розділи канону (персонажі, локації…) приходять зі Світу.

Кожен розділ має стандартні підзаголовки, однакові для будь-якої гри. Наприклад, Механіки: Рух, Бій, Здібності, Взаємодія, Камера й керування, Смерть і відродження, Перемога й поразка. Автор додає власні. Стандартні підзаголовки знає й AI: імпорт нотаток і scaffold плану розкладають картки по них.

## 5. Task Engine — специфікація

### 5.1. Статуси і переходи

| Статус | Хто переводить | Значення |
|---|---|---|
| todo | Сервер (план), автор (розблокувати) | Чекає. «Готове», якщо всі deps у done. |
| in_progress | Claude Code: get_next_task | Виконавець працює; report_task_progress показує прогрес наживо. |
| blocked | Claude Code: report_blocker | Потрібен автор (немає ассета, суперечність). Автор відповідає → todo. |
| review | Claude Code: submit_task_result | Звіт: підсумок, файли, коміт, тести, критерії з доказами + серверний check. |
| rework | Автор: «Повернути» з коментарем | Повертається тому самому виконавцю першим у черзі. |
| done | Автор: «Прийняти» | Повʼязані картки отримують статус «в грі». Прогрес плану росте. |

### 5.2. Правила

- Наступне завдання: спершу продовжується in_progress, потім rework, далі перше готове todo за порядком плану.
- Новий план замінює лише відкриті завдання (todo/rework). Взяті, на рев’ю і виконані зберігаються.
- Критерії приймання (2–5) і тести генеруються з планом. Вони конкретні й перевірювані: «префаб вовка зʼявляється на доріжці 2 з HP 60».
- Сервер сам рахує check: allCriteriaMet, unmet[], testsGreen. Рішення приймає автор, а не AI.
- Кожен виклик MCP пишеться в executions — стрічка активності в Біблії.

## 6. MCP — специфікація інтеграції

### 6.1. Транспорт і авторизація

| Параметр | Значення |
|---|---|
| Endpoint | https://us-central1-whitewrite-app.cloudfunctions.net/mcp |
| Транспорт | MCP Streamable HTTP, stateless JSON-RPC: initialize, tools/list, tools/call, ping. Нотифікації → 202, GET → 405. |
| Версії протоколу | 2025-06-18, 2025-03-26, 2024-11-05 |
| Авторизація | Authorization: Bearer wwk_… → sha256 → mcpKeys (не відкликаний) → план власника має allowGameDev. Перевіряється на кожен виклик. |
| Скоуп | Один ключ = одна гра. Параметри клієнта не розширюють доступ: світ і гра беруться з ключа. |
| Помилки | Невірний ключ → 401 JSON-RPC (-32001). Помилки інструмента → result з isError і текстом причини. |

Підключення (ключ показується один раз у Біблія гри → Продакшн-план → Підключити Claude Code):

```
claude mcp add --transport http whitewrite \
  https://us-central1-whitewrite-app.cloudfunctions.net/mcp \
  --header "Authorization: Bearer wwk_…"
```

| Інструмент | Призначення | Вхід → ефект |

### 6.3. Відповідь на питання v2 (Крок 2): чи потрібен локальний Bridge?

Для MVP — ні. Віддаленого MCP-сервера через HTTP достатньо. Claude Code запускається в папці Unity-проєкту і вже має все для технічної роботи: читання й редагування файлів, shell, git, запуск Unity у batch-режимі для EditMode/PlayMode тестів. WhiteWrite дає йому лише те, чого локально немає: затверджений задум, контекст завдання, файли ассетів і канал звітування.

Локальний Bridge або Unity Editor Plugin знадобиться, коли потрібна буде жива взаємодія з відкритим редактором (сцена, інспектор, скриншоти Play Mode) або автозапуск виконавця без людини. Це Фаза 6.

> Перевірено на проді: справжній Claude Code CLI підключився до сервера, прочитав огляд гри MythRunner (19 сутностей канону, 131 картка ассетів із FBX і текстурами) і коректно відповів. get_next_task без плану повертає «No roadmap yet».

## 7. Робочий цикл Claude Code

1. Автор у Біблії: заповнює розділи (або імпортує .md), натискає «Оновити аналіз», потім «Перегенерувати план». Завдання записуються в tasks/.
2. Автор натискає «Підключити Claude Code» і виконує показану команду в терміналі в папці Unity-проєкту.
3. Claude Code: get_project_overview → get_next_task. Завдання стає «в роботі», автор бачить це наживо.
4. Claude Code досліджує проєкт і фреймворк, реалізує, звітує report_task_progress, за потреби тягне картки й файли (get_card, get_design_section).
5. Якщо бракує ассета або рішення — report_blocker. Якщо треба змінити задум — submit_change_request. Сам GDD він не змінює.
6. Запускає тести, комітить, викликає submit_task_result з критеріями й доказами.
7. Автор бачить звіт і серверний check. «Прийняти» → done, картки «в грі». «Повернути» → rework з коментарем.
8. Claude Code бере наступне завдання.

Рекомендований фрагмент CLAUDE.md у репозиторії Unity-гри:

```
Задум і план гри живуть у WhiteWrite (MCP-сервер whitewrite).
На старті: get_project_overview, потім get_next_task.
Працюй лише в межах завдання. Не змінюй GDD, канон чи архітектуру —
  для цього submit_change_request.
Повідомляй прогрес report_task_progress; якщо застряг — report_blocker.
Перед здачею: тести (EditMode/PlayMode), коміт, submit_task_result
  з кожним критерієм приймання і доказом.
```

## 9. Безпека

- Ключ wwk_ показується один раз. У базі лише його sha256, видно тільки префікс.
- Ключ привʼязаний до однієї гри. Світ і гра беруться з ключа, а не з параметрів клієнта.
- Кожен виклик перевіряє, що ключ не відкликаний і план власника досі дає allowGameDev.
- Відкликання: у Біблії (для гри) і в Акаунт → Інтеграції (усі ключі). Діє миттєво.
- Firestore rules: світ і гра — лише власник. Запис гри вимагає плану з allowGameDev. Ключ створюється лише для свого світу, з фіксованим набором полів, без оновлень із клієнта.
- Виконавець не змінює затверджені рішення напряму. Для цього є лише change request, рішення за автором.
- Журнал executions фіксує кожну дію виконавця.
- Далі: Git checkpoints у звіті (коміт уже передається), рівні дозволів ключа (читання / виконання), ліміти частоти.

| A. E2E на реальній грі | MythRunner: імпорт нотаток → аналіз → план → Claude Code виконує 2–3 завдання в Unity-проєкті. Зібрати, що бракує в контексті. |
| B. Framework Registry | Аудит власного Unity/RPG Framework. Каталог модулів (API, приклади, залежності, версія) як розділ або колекція. Інструменти search_framework_modules, get_framework_module. План посилається на модулі. |
| C. GDD Workflow | Статуси розділів (Not Started → Approved → Needs Revision), рішення з обґрунтуванням і версіями, діалог AI по розділу. |
| D. Граф залежностей гри | Розширити рушій реконструкції: зміна картки або рішення → вплив на завдання й ассети → пропозиція переглянути, а не автоматичне скасування. |
| E. Asset Pipeline | ТЗ ассета (формат, полікаунт, LOD, pivot, колайдер), залежності model → material → prefab, report_asset_status. Генерація 2D/3D. |
| F. Інтеграції | REST API і вебхуки, Unity Editor Plugin (жива сцена), Blender, інші виконавці. Сервер керує завданнями незалежно від того, хто їх виконує. |
| G. Екосистема | Публікація, каталог ігор, спільнота — після стабільного циклу розробки. |

## 11. Головний принцип

WhiteWrite — мозок і памʼять гри: канон світу, Біблія, рішення, план і стан. Claude Code — виконавець, що думає самостійно в межах завдання. Unity — середовище реалізації. Власний Unity Framework — технологічний фундамент.

Автор описує світ і гру, ухвалює рішення і приймає роботу. Платформа знає, що робити далі, дає виконавцю рівно потрібний контекст і перевіряє результат проти затвердженого задуму.
