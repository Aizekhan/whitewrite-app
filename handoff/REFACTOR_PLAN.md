# REFACTOR_PLAN — WhiteWrite архітектурна стабілізація

> Великий рефакторинг, але СУВОРО по фазах. Прод лишається робочим після КОЖНОЇ
> фази. Жодного «навалом». Один модуль → димовий тест → деплой → комміт → далі.

## Що ми робимо (суть)
Логіка зараз розмазана по 5 файлах, один функціонал шукають всюди, немає єдиного
джерела правди. Мета — **чиста архітектура з shared source-of-truth**, без переписування
всього одразу. Економіка (ціни/логи) — це ОДИН із шарів, не окремий проєкт.

## Залізні правила
1. Гілка `refactor`, тег `stable-book` на робочому коміті. Прод на `main` — страховка для відкату.
2. Прод працює після КОЖНОЇ фази (не накопичувати зміни).
3. Кожна фаза: МЕТА / ФАЙЛИ / НЕ ЧІПАЙ / ГОТОВО КОЛИ → димовий тест → деплой → комміт.
4. Перед великим обсягом коду — спитати. Не «спрощувати» й не вигадувати UI.
5. Один source of truth на систему (див. SYSTEM_REGISTRY.md).

## ФАЗИ (саме в цьому порядку)

### Phase 0 — Повернути зламане
- Поверни зниклий **ритуал-генерації** (StartStoryAnim/прогрес очікування сцени).
- Будь-що інше, що зламалось останніми днями.
- ГОТОВО КОЛИ: створив→генерація показує ритуал→книга показує сцену. Прод стабільний.

### Phase 1 — ARCHITECTURE.md (тільки текст, нуль коду)
- Карта: де живе кожен функціонал (shell, книга, пагінація, генерація, токени,
  канон, AI, projectId, навігація, економіка). Файл → відповідальність.
- ГОТОВО КОЛИ: я бачу карту, де однозначно «де що живе».

### Phase 2 — SYSTEM_REGISTRY.md (таблиця джерел правди)
| Система | Source of Truth |
|---|---|
| Project | currentProjectId (ProjectContext) |
| Economy | economy_operations |
| Canon | canon document у project |
| Scenes | scenes subcollection |
| User Plan | users/{uid} |
| Token Balance | token-service |
| AI Models | ai-models.js |
- ГОТОВО КОЛИ: один файл відповідає «де зберігається X».

### Phase 3 — Один projectId
- Звести `window.__currentProjectId` / `PROJECT_ID` / urlParams → ОДИН `ProjectContext`.
- ГОТОВО КОЛИ: один доступ до projectId; книга/всесвіт/режисер читають з нього; димовий тест.

### Phase 4 — Economy Layer (мінімум, що працює)
- `economy_operations` колекція + seed: `{generateScene:300, extractCanon:20, analyzeScene:50}` (ціни як ДАНІ, не магічні числа).
- `generateScene` читає ціну з economy_operations → **ОДРАЗУ фіксить баг «Claude 20 замість 300»**.
- `usage_logs`: лог на операцію — `{operation, provider, model, inputTokens, outputTokens, apiCostUSD, userTokens, uid, projectId, timestamp}`.
- ТІЛЬКИ claude+gemini. images/storage/embedding/Dashboard — ПОТІМ (Phase 2 економіки, не зараз).
- ГОТОВО КОЛИ: згенерував Claude-сцену → списалось 300 (не 20) → лог записався. Скрін Firestore + лог.

### Phase 5 — token-service
- Винести всю логіку токенів (баланс, споживання, feature-gates) в один сервіс, що читає economy_operations.
- ГОТОВО КОЛИ: усі списання йдуть через token-service; димовий тест.

### Phase 6 — scene-service / project-service
- CRUD проєктів і сцен — у свої сервіси. UI лише викликає.
- ГОТОВО КОЛИ: створення/читання/збереження працюють через сервіси.

### Phase 7 — generation-controller (найкритичніший — останнім)
- `startGeneration / updateProgress / saveScene / consumeTokens / finishGeneration` в одному місці.
- Прибрати бізнес-логіку з onClick → `handleGenerate()` → controller.
- ГОТОВО КОЛИ: генерація+прогрес+токени+помилки живуть в одному контролері; наскрізний цикл працює.

### Phase 8 — CSS-змінні геометрії книги
- Магічні числа (top/bottom/left/right) → `--page-*` в одному місці.
- ГОТОВО КОЛИ: зміна одного `--page-*` рухає текст; нічого не шукати по 5000 рядках.

> Порядок: спершу бізнес-критичне (економіка, projectId, генерація), CSS — наприкінці
> (не впливає на бізнес). Прод робочий після кожної фази.
